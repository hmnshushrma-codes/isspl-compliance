1. Purpose

The Security Incident Register is the authoritative log of all security incidents detected, reported, and managed at Ramdoot Solutions. It captures the full lifecycle of each incident from initial detection through containment, eradication, recovery, and post-incident review. The register enables trending, root cause analysis, and continuous improvement of the organisation's security posture.

This register supports the Incident Response Plan (RS-SEC-004), SOC 2 Trust Services Criteria CC7.2 (monitoring for anomalies), CC7.3 (security incidents), CC7.4 (incident response), and CC7.5 (incident recovery), as well as CERT-In notification requirements under Indian IT Act provisions.

2. How to Use This Register

Instructions for Incident Managers:

  1. Detection: When a security incident is detected or reported, create a new entry immediately. Assign a unique Incident ID (format: INC-YYYY-NNN).
  2. Triage: Assess the severity (P1-P4) and assign the incident to the appropriate response team.
  3. Containment: Document all containment actions taken, including timestamps.
  4. Investigation: Record investigation findings, systems affected, and scope of impact.
  5. Resolution: Document the resolution steps and confirm the incident is fully resolved.
  6. Root Cause: Conduct root cause analysis (RCA) for all P1 and P2 incidents. Optionally for P3/P4.
  7. Lessons Learned: Document lessons learned and recommendations. Update controls, policies, or procedures as needed.
  8. Closure: Mark the incident as Closed only after all remediation actions are complete and verified.
  9. Reporting: P1 incidents must be reported to senior management within 1 hour. Incidents involving personal data breach must be reported to CERT-In within 6 hours as per CERT-In Direction of April 2022.

3. Severity Classification

Severity Description Examples Response Time Escalation
P1 — Critical Severe impact on business operations, data integrity, or confidentiality. Active ongoing threat. Service outage affecting clients. Active data breach, ransomware attack, production system compromise, critical data exfiltration Immediate response (within 15 minutes) CISO, Senior Management, Legal — within 1 hour. CERT-In within 6 hours if data breach.
P2 — High Significant impact on security or operations. Threat is contained but unresolved. Potential for escalation. Successful phishing (credentials exposed), unauthorised access detected, malware on endpoint, partial service degradation Response within 1 hour CISO, IT Manager — within 4 hours
P3 — Medium Moderate impact. No confirmed data exposure. Limited operational effect. Phishing email received (not clicked), policy violation detected, suspicious login attempt, vulnerability discovered Response within 4 hours IT Manager — within 24 hours
P4 — Low Minor issue with negligible impact. Informational or precautionary. Failed login attempts, spam increase, minor configuration drift, security scan false positive Response within 1 business day IT Manager — at next scheduled review

Incident ID Format: INC-[YEAR]-[SEQ] — for example, INC-2026-001 is the first incident recorded in 2026. Sequence numbers are assigned chronologically and never reused.

5. Incident Lifecycle

Each incident progresses through the following stages. The current stage should be reflected in the Status column of the register.

Stage Status Value Description Key Actions
1. Detection New Incident reported or detected by monitoring systems Create register entry, assign ID, notify incident manager
2. Triage Triaging Initial assessment of severity, scope, and impact Classify severity (P1-P4), assign response team, initiate escalation if needed
3. Containment Containing Actions taken to limit the spread and impact of the incident Isolate affected systems, block malicious IPs, disable compromised accounts, preserve evidence
4. Eradication Eradicating Remove the root cause of the incident Remove malware, patch vulnerabilities, close attack vectors, restore from clean backups
5. Recovery Recovering Restore systems and services to normal operation Restore services, verify system integrity, monitor for recurrence, communicate with stakeholders
6. Post-Incident Review Under Review Analyse the incident, identify root cause, and document lessons learned Conduct RCA, document timeline, update risk register, implement improvements
7. Closed Closed All actions complete, lessons documented, register entry finalised Archive evidence, update policies/controls as needed, close register entry

P2 incidents CISO, IT Manager Within 4 hours Email + incident tracking system
Monthly summary Security and Compliance Committee Monthly Incident summary report

7. Metrics and Reporting

The following metrics are derived from this register and reported quarterly to the Security and Compliance Committee:

  • Total incidents by severity: Count of P1, P2, P3, P4 incidents per quarter
  • Mean Time to Detect (MTTD): Average time from incident occurrence to detection
  • Mean Time to Contain (MTTC): Average time from detection to containment
  • Mean Time to Resolve (MTTR): Average time from detection to full resolution
  • Incident categories: Breakdown by type (malware, phishing, unauthorised access, data loss, etc.)
  • Repeat incidents: Count of incidents with the same root cause as a prior incident
  • Overdue incidents: Incidents exceeding their response or resolution SLAs
