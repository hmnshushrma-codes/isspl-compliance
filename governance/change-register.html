1. Purpose

The Change Management Register tracks all changes to production IT systems, infrastructure, applications, and configurations at Ramdoot Solutions. Effective change management reduces the risk of unplanned outages, security vulnerabilities, and service degradation by ensuring all changes are assessed, approved, tested, and documented before implementation.

This register supports the Change Management Procedure (RS-PROC-004), SOC 2 Trust Services Criteria CC8.1 (change management), and aligns with ITIL change management best practices.

2. How to Use This Register

Instructions for Change Requesters:

  1. Submit: Create a new entry with a unique Change ID (format: CHG-YYYY-NNN). Describe the change, its business justification, and systems affected.
  2. Risk Assessment: Evaluate the risk level (Low/Medium/High/Critical) based on scope of impact, complexity, and reversibility.
  3. Approval: Route the change for approval based on its risk level (see Section 3). No changes should be implemented without documented approval.
  4. Testing: Where feasible, test the change in a non-production environment before implementation. Document test results.
  5. Rollback Plan: Every change must have a documented rollback plan. If the change cannot be safely rolled back, this must be explicitly noted and approved.
  6. Implementation: Implement the change during the approved maintenance window. Follow the implementation plan.
  7. Post-Implementation Review: After implementation, verify the change was successful. Document any issues encountered.
  8. Closure: Update the register with the final status and close the change request.

3. Change Categories and Approval Requirements

Category Description Risk Level Approver Lead Time
Standard Pre-approved, routine changes with well-understood risk and established procedures (e.g., regular patching, user account creation) Low IT Manager (pre-approved) As per schedule
Normal Non-routine changes requiring individual assessment and approval (e.g., application deployment, configuration change, infrastructure upgrade) Medium IT Manager + CISO review Minimum 3 business days
Major High-impact changes affecting critical systems or multiple services (e.g., database migration, architecture change, new system deployment) High Change Advisory Board (CAB) Minimum 5 business days
Emergency Urgent changes required to resolve a critical incident or address an immediate security vulnerability. Bypasses normal approval timelines. Critical CISO or Senior Management (verbal, with retrospective documentation) Immediate (post-approval within 48 hours)

8. Metrics and Reporting

The following metrics are derived from this register and reported monthly to the IT Manager and quarterly to the Security and Compliance Committee:

  • Total changes by category: Count of Standard, Normal, Major, Emergency changes per period
  • Change success rate: Percentage of changes completed successfully without rollback
  • Emergency change ratio: Percentage of emergency changes vs. total changes (target: below 10%)
  • Failed changes: Count and details of changes that were rolled back or failed
  • Unauthorised changes: Changes implemented without proper approval (should be zero)
  • Average lead time: Average time from submission to implementation
