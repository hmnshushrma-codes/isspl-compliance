1. Purpose

This procedure defines the processes for backing up and restoring data and system configurations across Ramdoot Solutions' information systems. It ensures that critical data can be recovered in the event of hardware failure, software corruption, accidental deletion, cyber attack (including ransomware), or disaster, meeting the organization's Recovery Point Objectives (RPO) and Recovery Time Objectives (RTO).

2. Scope

This procedure covers:

  • All production databases (relational, NoSQL, object storage).
  • Application server configurations and deployment artifacts.
  • Infrastructure configurations (network devices, firewall rules, cloud resource templates).
  • File shares and document repositories containing business-critical data.
  • Email systems and collaboration platform data.
  • Source code repositories (mirrored backups).
  • Certificates, keys, and secrets (encrypted backup).

Individual endpoint (laptop/desktop) backups are the responsibility of each employee using the corporate endpoint backup agent; this procedure covers server-side and infrastructure backups.

3. Definitions

TermDefinition
RPO (Recovery Point Objective)The maximum acceptable amount of data loss measured in time. An RPO of 4 hours means backups must be frequent enough that no more than 4 hours of data is lost.
RTO (Recovery Time Objective)The maximum acceptable time to restore a system to operational status after a disruption.
Full BackupA complete copy of all data in the backup set.
Incremental BackupA copy of only the data that has changed since the last backup (full or incremental).
Differential BackupA copy of all data that has changed since the last full backup.
Offsite ReplicationCopying backup data to a geographically separate location for disaster recovery.
Backup Integrity CheckVerification that backup data is complete, uncorrupted, and restorable.

5. Prerequisites

  • Backup infrastructure (storage, software, network bandwidth) is provisioned and tested.
  • RPO and RTO targets are documented for each critical system.
  • Encryption keys for backup encryption are securely managed and escrowed.
  • Offsite/cloud backup storage is contracted and accessible.
  • Monitoring and alerting are configured for backup job success/failure.

6. Step-by-Step Procedure

6A. Backup Procedure

Step 1: Schedule Verification

Performed by: IT Operations / Backup Administrator

  1. Review the backup schedule at the beginning of each month to ensure it aligns with current RPO requirements:
Data TypeBackup TypeFrequencyRetentionRPO Target
Production DatabasesFull + WAL/Transaction LogFull: Daily, WAL: Continuous30 days (daily), 12 months (monthly)≤ 1 hour
Application ConfigsFullDaily30 days≤ 24 hours
File Shares / DocumentsFull + IncrementalFull: Weekly, Incr: Daily30 days (daily), 12 months (monthly)≤ 24 hours
Email / CollaborationIncremental (SaaS-native)DailyPer SaaS provider retention + 90 days export≤ 24 hours
Infrastructure ConfigsFull (IaC export)After every change + Weekly90 days≤ 24 hours
Secrets / CertificatesFull (encrypted)After every change + Monthly12 months≤ 24 hours
  1. Verify all backup jobs are enabled and scheduled correctly in the backup management console.
  2. Confirm backup storage capacity is sufficient for the next 30 days of growth.

Step 2: Backup Execution

Performed by: Automated / Backup Administrator

  1. Backup jobs execute automatically per the defined schedule.
  2. For database backups: full backups run during the designated maintenance window (off-peak hours); WAL/transaction log archiving runs continuously.
  3. For file-level backups: incremental backups run nightly; full backups run weekly.
  4. The backup system logs the start time, end time, data volume, and completion status for each job.

Step 3: Integrity Check

Performed by: Backup Administrator

  1. After each backup completes, verify the integrity:
    • Check the backup log for errors or warnings.
    • Validate checksum / hash of the backup file.
    • For database backups: verify the backup can be listed and metadata is consistent.
  2. Monthly, perform a test restore of a randomly selected backup to an isolated environment to confirm recoverability (see Restore Step 3 below).
  3. Document integrity check results in the Backup Log.

Step 4: Offsite Replication

Performed by: Automated / Backup Administrator

  1. All backups are replicated to the offsite/cloud storage location within 4 hours of completion.
  2. Replication uses encrypted transfer (TLS in transit, AES-256 at rest).
  3. Verify replication success by checking the offsite storage inventory against the primary backup log.
  4. The offsite location is in a different geographic region from the primary data centre.

Step 5: Monitoring

Performed by: Backup Administrator / Monitoring System

  1. Monitor backup job status daily via the backup management dashboard.
  2. Automated alerts are sent for:
    • Backup job failure or partial completion.
    • Backup storage reaching 80% capacity.
    • Offsite replication failure or lag exceeding 8 hours.
  3. Investigate and resolve backup failures within 4 hours. If a backup cannot be completed, escalate to the IT Manager and re-run the backup manually.
  4. Generate a weekly backup status report summarizing: jobs run, success rate, storage used, and any failures with resolution.

6B. Restore Procedure

Step 1: Request Authorization

Performed by: System/Application Owner / Requestor

  1. Submit a "Restore Request" ticket specifying:
    • System/data to be restored.
    • Reason for the restore (accidental deletion, corruption, disaster recovery, testing).
    • Target restore point (date/time or specific backup ID).
    • Target environment (production or isolated/test).
  2. The System/Application Owner approves the request. For production restores, the IT Manager must also approve.

Step 2: Backup Identification

Performed by: Backup Administrator

  1. Identify the appropriate backup based on the requested restore point.
  2. Verify the backup integrity (checksum, completeness) before proceeding.
  3. If the primary backup is unavailable or corrupt, use the offsite replica.
  4. Document the selected backup (ID, date, location) in the restore ticket.

Step 3: Restore to Isolated Environment

Performed by: Backup Administrator / DBA

  1. Restore the backup to an isolated (non-production) environment first, unless this is an emergency production restore.
  2. Execute the restore using the documented restore procedure for the specific system type (database restore, file restore, configuration restore).
  3. Record the restore start time and monitor progress.

Step 4: Integrity Verification

Performed by: Backup Administrator / System Owner

  1. Verify the restored data:
    • Database: check row counts, run consistency checks, verify recent transactions.
    • Files: verify file counts, directory structure, and spot-check critical files.
    • Configuration: verify settings match expected values and services start correctly.
  2. The System/Application Owner validates that the restored data meets their requirements.
  3. Document the verification results in the restore ticket.

Step 5: Production Cutover

Performed by: IT Operations / DBA

  1. If the restore is destined for production:
    • Follow the Change & Release Procedure (RS-PRO-007) — emergency change sub-procedure for urgent restores.
    • Take a snapshot/backup of the current production state before overwriting.
    • Execute the production restore or promote the verified restore from the isolated environment.
    • Verify production system functionality and data integrity post-cutover.
  2. Notify affected stakeholders that the restore is complete.

Step 6: Documentation

Performed by: Backup Administrator

  1. Complete the restore ticket with: backup used, restore timeline, verification results, and any issues encountered.
  2. Update the Backup Log with the restore event.
  3. If the restore was triggered by a data loss incident, link the restore ticket to the incident ticket (RS-PRO-005).

7. Verification / Completion Criteria

  • All scheduled backups complete successfully with documented integrity checks.
  • Offsite replication is current (within 4 hours of the latest backup).
  • Monthly test restores are completed and documented, confirming data recoverability.
  • Backup failures are resolved within 4 hours and no RPO targets are breached.
  • Restore operations meet the defined RTO targets.
  • Weekly backup status reports are generated and reviewed.

9. Exceptions

Exceptions must be approved by [TO BE COMPLETED BY RAMDOOT SOLUTIONS].

  • Non-Critical Development Data: Development and test databases that contain only synthetic data may have relaxed backup schedules (weekly full only) with documented approval from the System Owner.
  • SaaS-Managed Backups: For SaaS platforms where the provider manages backups (e.g., Google Workspace, Microsoft 365), the provider's backup SLA is accepted, supplemented by periodic data exports stored in the organization's offsite storage.
  • Temporary Backup Gaps: If backup infrastructure maintenance causes a gap exceeding 24 hours, the IT Manager must approve and a manual backup must be taken before and after the maintenance.
