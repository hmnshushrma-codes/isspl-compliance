1. Purpose

This procedure defines the standardized process for requesting, approving, modifying, and revoking access to information systems, applications, and data at Ramdoot Solutions. It ensures that all access is granted on a need-to-know and least-privilege basis, with proper authorization and documentation at every stage.

2. Scope

This procedure applies to:

  • All access requests for production systems, SaaS applications, cloud infrastructure, databases, file shares, and code repositories.
  • All employees, contractors, and temporary staff of Ramdoot Solutions.
  • Access requests for new access, access changes (role modifications), and access removal.

Privileged/administrative access follows the supplementary Privileged Access Procedure (RS-PRO-004).

5. Prerequisites

  • The beneficiary must have an active employee/contractor record in the HRIS.
  • The requestor must have access to the IT ticket system.
  • For new employees, the onboarding process (RS-PRO-001) must have been initiated.
  • The system or application must be registered in the IT service catalogue with a defined Data Owner.

6. Step-by-Step Procedure

6A. New Access Request

Step 1: Request Submission

Performed by: Requestor

  1. Open a new "Access Request" ticket in the IT ticket system.
  2. Complete all mandatory fields:
    • Beneficiary name and employee ID
    • System / application name
    • Specific role or access level requested
    • Business justification (why this access is needed)
    • Duration (permanent or time-limited)
  3. Submit the ticket; the system routes it to the Line Manager for approval.

Step 2: Manager Approval

Performed by: Line Manager

  1. Review the request within 2 business days.
  2. Confirm the beneficiary's role requires the requested access.
  3. Verify the access level adheres to the principle of least privilege.
  4. Approve or reject the request with comments. If rejected, the requestor is notified with the reason.

Step 3: Security Review

Performed by: Information Security Team

  1. Review all requests involving sensitive data (Confidential or Restricted classification), cross-department access, or production system access.
  2. Validate that the access does not create segregation-of-duties conflicts.
  3. Check for existing access that may overlap or conflict with the request.
  4. Approve, reject, or request modifications. For routine/low-risk access, this step may be auto-approved based on predefined rules.

Step 4: Access Provisioning

Performed by: IT Operations / System Admin

  1. Provision the approved access exactly as specified in the ticket.
  2. Enable MFA if not already configured on the target system.
  3. Set the access expiry date for time-limited requests.
  4. Document the provisioned access in the Access Management Log.

Step 5: Confirmation

Performed by: IT Operations / Requestor

  1. IT notifies the requestor and beneficiary that access has been provisioned.
  2. The beneficiary verifies they can access the system with the correct permissions.
  3. If there are issues, the beneficiary re-opens the ticket for correction.

Step 6: Documentation

Performed by: IT Operations

  1. Close the ticket with a summary of access granted, approval chain, and provisioning date.
  2. Update the user's access profile in the Access Management Log.
  3. The ticket and all approvals are retained as audit evidence.

6B. Access Change Sub-Procedure

When an employee's role changes (promotion, transfer, project reassignment), their access must be reviewed and modified:

  1. The Line Manager submits an "Access Change" ticket specifying the access to be added and/or removed.
  2. The request follows Steps 2–6 of the New Access Request procedure above.
  3. Critically, access that is no longer required for the new role must be explicitly removed. The ticket must list both additions and removals.
  4. The Information Security Team verifies that the combined access (existing + new) still adheres to least privilege and segregation of duties.

6C. Access Removal Sub-Procedure

When access is no longer required (project completion, role change, or manager-initiated removal):

  1. The Line Manager or HR submits an "Access Removal" ticket identifying the specific access to be revoked.
  2. IT Operations revokes the access within 1 business day of approval.
  3. For employee offboarding, the removal is handled under RS-PRO-002 with same-day or last-day revocation timelines.
  4. IT Operations updates the Access Management Log and closes the ticket.

7. Verification / Completion Criteria

  • Every access request has a closed ticket with complete approval chain documented.
  • The Access Management Log reflects the current state of all user access.
  • Time-limited access has an expiry date set and is automatically revoked or flagged for review.
  • Quarterly access reviews confirm that all active access is still justified.
  • No access is provisioned without documented manager approval.

9. Exceptions

All exceptions require approval from [TO BE COMPLETED BY RAMDOOT SOLUTIONS].

  • Emergency Access: In critical incidents (P1/P2), emergency access may be provisioned with verbal manager approval. A formal ticket must be raised and approved retrospectively within 24 hours. Emergency access is logged separately and reviewed by Information Security within 48 hours.
  • Bulk Access Requests: For new project teams requiring identical access, a single bulk request may be submitted listing all beneficiaries. Each individual's access is still logged separately in the Access Management Log.
