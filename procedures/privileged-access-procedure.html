1. Purpose

This procedure governs the request, approval, provisioning, monitoring, review, and revocation of privileged access (administrative, root, superuser, or elevated permissions) across all Ramdoot Solutions information systems. Privileged accounts carry significantly higher risk than standard user accounts because they can bypass security controls, access sensitive data, and modify system configurations. This procedure ensures such access is tightly controlled, time-limited where possible, continuously monitored, and regularly recertified.

2. Scope

This procedure applies to:

  • All privileged accounts including: root/administrator accounts, database administrator accounts, cloud console admin roles, service accounts with elevated permissions, and break-glass/emergency accounts.
  • All employees, contractors, and third-party personnel who require privileged access to any Ramdoot Solutions system.
  • All environments: production, staging, and disaster recovery.

Standard (non-privileged) access requests follow RS-PRO-003.

5. Prerequisites

  • The requestor must have an active standard access account in good standing (no policy violations).
  • Multi-factor authentication (MFA) must be enabled on the requestor's identity provider account.
  • The requestor must have completed the annual Security Awareness Training and any privileged-user-specific training.
  • The target system must be enrolled in the PAM platform (or have manual equivalent controls documented).

6. Step-by-Step Procedure

Step 1: Business Justification

Performed by: Requestor

  1. Submit a "Privileged Access Request" ticket in the IT ticket system.
  2. Provide a detailed business justification including:
    • The specific system(s) and the privileged role/permission required.
    • The tasks that require elevated access (e.g., server configuration, database migration, incident remediation).
    • The requested duration — privileged access must be time-limited. Permanent privileged access requires exceptional justification.
    • Confirmation that the task cannot be accomplished with standard access.
  3. Attach any supporting documentation (change ticket, incident ticket, project plan).

Step 2: Security Officer Approval

Performed by: Line Manager, then Security Officer

  1. The Line Manager reviews and endorses the request, confirming the business need.
  2. The Security Officer reviews the request within 1 business day, assessing:
    • Whether the justification is adequate and specific.
    • Whether the requested access level is the minimum necessary (least privilege).
    • Whether the duration is appropriate — preferring Just-In-Time (JIT) access.
    • Whether there are segregation-of-duties conflicts.
    • The requestor's access history and any prior policy violations.
  3. Approve with conditions (time limit, monitoring level), reject with documented reason, or request additional information.

Step 3: Time-Limited Provisioning

Performed by: IT Operations / PAM Administrator

  1. Provision the privileged access exactly as approved, using the PAM platform where available.
  2. Set the automatic expiration date/time as specified in the approval.
  3. Configure session recording and keystroke logging for the privileged session (where technically feasible).
  4. Ensure the privileged account uses a unique credential (not shared) and requires MFA at each login.
  5. Notify the requestor that access is active and remind them of the expiration time and usage conditions.

Step 4: Activity Logging

Performed by: PAM Platform / IT Operations

  1. All actions performed under the privileged account are logged with timestamps, source IP, and command/action details.
  2. Logs are forwarded to the centralized SIEM in real time.
  3. Alerts are configured for high-risk actions (e.g., bulk data exports, security setting changes, user creation).
  4. Logs are immutable and tamper-protected; privileged users cannot modify their own activity logs.

Step 5: Periodic Review (Monthly)

Performed by: Information Security Team

  1. On a monthly basis, generate a report of all active privileged access grants.
  2. Review each grant:
    • Is the access still needed? Has the task or project been completed?
    • Has the access been used? Unused privileged access should be revoked.
    • Were there any anomalous activities in the session logs?
  3. Contact the Line Manager and requestor for confirmation of continued need.
  4. Revoke access where it is no longer justified.
  5. Document the review findings and actions taken.

Step 6: Access Recertification

Performed by: Information Security Team / Security Officer

  1. Quarterly, conduct a formal recertification of all standing (non-JIT) privileged access.
  2. Each privileged access holder's Line Manager must explicitly recertify or revoke.
  3. The Security Officer reviews the recertification results and approves the continued access or mandates revocation.
  4. Recertification records are maintained as audit evidence.
  5. Any access not recertified within 5 business days of the review deadline is automatically suspended.

Step 7: Revocation When No Longer Needed

Performed by: IT Operations / PAM Administrator

  1. Privileged access is revoked immediately when:
    • The approved time window expires (automatic).
    • The task or project requiring the access is completed.
    • The employee changes roles or leaves the organization.
    • A security concern or policy violation is identified.
    • The access is not recertified during the quarterly review.
  2. Update the Access Management Log and close the associated ticket.
  3. Rotate any shared credentials that the revoked user had access to.

7. Verification / Completion Criteria

  • All privileged access requests have a completed ticket with Security Officer approval on file.
  • No privileged access exists without a documented business justification and expiration date.
  • Monthly reviews are completed and documented with action items resolved.
  • Quarterly recertification achieves 100% coverage of standing privileged access.
  • All privileged sessions have corresponding activity logs in the SIEM.
  • Break-glass account usage is reviewed within 24 hours of each use.

9. Exceptions

Exceptions must be approved in writing by [TO BE COMPLETED BY RAMDOOT SOLUTIONS].

  • Break-Glass Access: In a P1 incident where the Security Officer is unavailable, the IT Manager may authorize break-glass account usage. The Security Officer must be notified within 1 hour, and a full post-use review must be completed within 24 hours.
  • Standing Privileged Access: Certain operational roles (e.g., DBA, infrastructure engineer) may require standing privileged access. These must be explicitly approved by the Security Officer, subject to quarterly recertification, and have enhanced monitoring enabled at all times.
