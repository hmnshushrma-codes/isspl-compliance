1. Purpose

This procedure governs the lifecycle of changes to production information systems at Ramdoot Solutions, from initial request through impact assessment, approval, implementation, and post-implementation review. It ensures that all changes are assessed for risk, authorized before implementation, tested adequately, and documented — minimizing the risk of service disruption and unauthorized modifications.

2. Scope

This procedure applies to all changes affecting:

  • Production and disaster recovery environments (servers, databases, network, cloud infrastructure).
  • Application code deployed to production.
  • Security configurations (firewall rules, WAF policies, IAM roles).
  • Third-party integrations and APIs.
  • Database schema changes and data migrations.
  • Infrastructure-as-code templates and CI/CD pipeline configurations.

Development and test environments are excluded from CAB review but must follow the testing requirements in this procedure before promoting to staging/production.

3. Definitions

TermDefinition
RFCRequest for Change — a formal proposal to modify a production system.
CABChange Advisory Board — the group that reviews and approves changes based on risk and impact.
Standard ChangeA pre-approved, low-risk, routine change (e.g., scheduled patching, minor config update) that follows a pre-defined procedure and does not require individual CAB review.
Normal ChangeA change that requires CAB review and approval before implementation.
Emergency ChangeAn urgent change needed to resolve a P1/P2 incident or address a critical vulnerability; follows an expedited approval path.
Rollback PlanA documented procedure to reverse the change and restore the prior state if the implementation fails.
PIRPost-Implementation Review — a retrospective assessment of the change after deployment.

5. Prerequisites

  • A ticketing system is in place for RFC submission and tracking.
  • CAB membership is defined and meeting cadence established (weekly or bi-weekly).
  • Staging environment mirrors production for pre-deployment testing.
  • Backup procedures are executed before major changes (per RS-PRO-008).
  • CI/CD pipelines include automated testing gates.

6. Step-by-Step Procedure

6A. Normal Change Procedure

Step 1: RFC Submission

Performed by: Change Requestor

  1. Create an RFC ticket in the ticketing system with the following details:
    • Description of the change and its business justification.
    • Systems, services, and environments affected.
    • Proposed implementation date and maintenance window.
    • Dependencies on other changes or systems.
    • Rollback plan with step-by-step instructions and estimated rollback time.
    • Test plan and results from staging/pre-production testing.
    • Communication plan (who needs to be notified before, during, and after).
  2. Submit the RFC at least 3 business days before the next CAB meeting for normal changes.

Step 2: Impact Assessment

Performed by: Change Manager / Change Requestor

  1. Assess the change risk level (Low / Medium / High / Critical) based on:
    • Scope of impact (number of users, systems, services).
    • Complexity of the change.
    • Reversibility (can it be easily rolled back?).
    • Historical success rate of similar changes.
    • Security implications.
  2. Identify potential conflicts with other scheduled changes or maintenance windows.
  3. Document the impact assessment in the RFC ticket.

Step 3: CAB Review

Performed by: CAB Members

  1. The Change Manager presents the RFC at the CAB meeting.
  2. CAB members review: business justification, impact assessment, test results, rollback plan, and security implications.
  3. CAB decision:
    • Approved: The change is authorized for implementation on the proposed date.
    • Approved with conditions: Additional testing, modified timeline, or enhanced rollback plan required.
    • Deferred: More information needed; resubmit at the next CAB.
    • Rejected: The change is not approved with documented reasons.
  4. Record the CAB decision and any conditions in the RFC ticket.

Step 4: Approval

Performed by: Change Manager

  1. Confirm all CAB conditions have been met.
  2. Obtain formal sign-off from the Change Manager and any additional approvers (e.g., Security Officer for security-related changes).
  3. Schedule the implementation in the change calendar.
  4. Send pre-implementation notification to all affected stakeholders.

Step 5: Development & Testing

Performed by: Implementation Team / QA

  1. Complete development and code review (peer review required for all code changes).
  2. Execute unit tests, integration tests, and security tests.
  3. Deploy to staging environment and execute the full test plan.
  4. Obtain QA sign-off that staging testing passed.
  5. Ensure all automated CI/CD pipeline checks pass (linting, tests, security scans).

Step 6: Staging Deployment

Performed by: Implementation Team

  1. Deploy the change to the staging environment using the same process that will be used for production.
  2. Conduct user acceptance testing (UAT) if applicable.
  3. Verify the staging deployment matches the expected behaviour.
  4. Confirm the rollback procedure works by executing it in staging.

Step 7: Production Deployment

Performed by: Implementation Team

  1. Verify that a current backup exists (per RS-PRO-008).
  2. Begin the deployment within the approved maintenance window.
  3. Execute the deployment steps as documented in the RFC.
  4. Monitor system health, error rates, and performance metrics during and immediately after deployment.
  5. If critical issues are detected, execute the rollback plan immediately and notify the Change Manager.
  6. Send deployment completion notification to stakeholders.

Step 8: Post-Implementation Review (PIR)

Performed by: Change Manager / Implementation Team

  1. Conduct a PIR within 3 business days for High/Critical changes, 5 business days for Medium/Low changes.
  2. Review:
    • Was the change implemented as planned?
    • Did any issues occur during or after deployment?
    • Were the objectives of the change achieved?
    • Was the timeline and maintenance window adequate?
  3. Document lessons learned and update procedures if needed.

Step 9: Documentation

Performed by: Change Requestor / Change Manager

  1. Update the RFC ticket with: actual implementation date/time, outcome (success/rollback), any deviations from the plan, and PIR findings.
  2. Close the RFC ticket.
  3. Update system documentation, runbooks, and configuration records as applicable.

6B. Emergency Change Sub-Procedure

Emergency changes bypass the standard CAB meeting schedule but still require authorization and documentation.

  1. Initiation: The Change Requestor contacts the Change Manager and at least one CAB member (Security Officer for security changes, IT Manager for infrastructure changes) by phone or instant message.
  2. Verbal Approval: The Change Manager and one CAB member provide verbal approval. The decision and rationale are documented in the RFC ticket retroactively.
  3. Implementation: The change is implemented following Steps 7 of the normal procedure (backup, deploy, monitor).
  4. Retroactive Documentation: Within 24 hours, the Change Requestor completes the full RFC ticket including impact assessment, test results (if any), and rollback plan used.
  5. Retroactive CAB Review: The emergency change is reviewed at the next scheduled CAB meeting for compliance and lessons learned.

7. Verification / Completion Criteria

  • All production changes have an RFC ticket with documented approval before implementation.
  • Staging testing is completed and signed off before production deployment.
  • Rollback plans exist and are tested for all High/Critical changes.
  • PIR is completed for all changes.
  • Emergency changes have retroactive documentation and CAB review within 1 week.
  • No unauthorized changes are detected in production (verified via configuration monitoring).

9. Exceptions

Exceptions must be approved by [TO BE COMPLETED BY RAMDOOT SOLUTIONS].

  • Development/Test Environment Changes: Changes to non-production environments do not require CAB approval but must follow the testing and code review requirements before promotion to staging.
