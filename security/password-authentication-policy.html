2. Purpose

This policy establishes requirements for password management, multi-factor authentication (MFA), single sign-on (SSO), session management, and account lockout mechanisms at Ramdoot Solutions. Strong authentication is a foundational control for protecting information systems and data from unauthorized access.

3. Scope

This policy applies to:

  • All user accounts, service accounts, and administrative accounts on Ramdoot Solutions information systems.
  • All employees, contractors, consultants, and third-party users who authenticate to Ramdoot Solutions systems.
  • All authentication mechanisms, including passwords, MFA tokens, biometrics, SSO, and API keys.
  • All environments — production, staging, development, and disaster recovery.

4. Objectives

  1. Ensure that authentication mechanisms effectively verify user identities before granting access.
  2. Establish minimum password complexity and lifecycle requirements that balance security with usability.
  3. Mandate multi-factor authentication for sensitive and privileged access.
  4. Define session management controls to prevent session hijacking and unauthorized persistent access.
  5. Establish lockout policies to mitigate brute-force and credential-stuffing attacks.

5. Definitions

TermDefinition
Multi-Factor Authentication (MFA)An authentication method that requires the user to provide two or more verification factors — something they know, something they have, or something they are.
Single Sign-On (SSO)An authentication scheme that allows a user to log in with a single set of credentials to access multiple independent systems.
Password ComplexityRequirements governing the characters and length that a password must contain to be considered acceptable.
SessionA period of interaction between a user and a system, beginning with authentication and ending with logout or timeout.
Account LockoutThe automatic disabling of a user account after a defined number of consecutive failed authentication attempts.
Credential StuffingAn automated attack that uses stolen username/password pairs from data breaches to attempt login on other systems.
Password HashA one-way cryptographic representation of a password used for secure storage.
TOTPTime-Based One-Time Password — a temporary code generated by an authenticator application that changes at fixed intervals.

6. Roles and Responsibilities

6.1 Information Security Officer

The ISO shall define authentication standards, approve exceptions, and monitor compliance with this policy.

6.2 IT Administration

IT shall implement and enforce password complexity rules, MFA configurations, session management settings, and lockout policies across all systems. IT shall manage the identity provider (IdP) and SSO infrastructure.

6.3 Application Development Teams

Development teams shall ensure that applications adhere to the authentication requirements defined in this policy, including secure password storage (hashing with approved algorithms), session management, and MFA integration.

6.4 All Users

Every user is responsible for creating strong passwords, safeguarding their credentials, enrolling in MFA as required, and reporting suspected compromises immediately.

7. Policy Statements

7.1 Password Complexity Requirements

All passwords for Ramdoot Solutions systems shall meet the following minimum complexity requirements:

  • Minimum length: 12 characters.
  • Must contain at least one uppercase letter (A–Z).
  • Must contain at least one lowercase letter (a–z).
  • Must contain at least one numeric digit (0–9).
  • Must contain at least one special character (e.g., !@#$%^&*()_+-=).
  • Shall not contain the user's name, username, email address, or other easily guessable personal information.
  • Shall not be a commonly used password or appear in known breached-password databases.

7.2 Password Rotation

Password rotation is recommended every 90 days for standard user accounts. Systems shall enforce a password history of at least 12 previous passwords to prevent reuse. For privileged accounts, password rotation shall be mandatory every 60 days. Immediate password change is required if a compromise is suspected.

7.3 Multi-Factor Authentication (MFA)

MFA shall be mandatory for:

  • All remote access connections (VPN, remote desktop, cloud portals).
  • All privileged and administrative accounts.
  • Access to systems classified as Confidential or Restricted.
  • Access to email systems from external networks.
  • All cloud service administration consoles.

Approved MFA methods include TOTP-based authenticator applications, hardware security keys (FIDO2/U2F), and push-based authentication through approved providers. SMS-based OTP is discouraged and shall only be used as a fallback where no other method is technically feasible.

7.4 Single Sign-On (SSO)

Where technically feasible, Ramdoot Solutions shall implement SSO using an approved identity provider. SSO shall use industry-standard protocols (SAML 2.0, OpenID Connect, or OAuth 2.0). Applications that support SSO integration must use it; local authentication bypass is prohibited unless approved by the ISO.

7.5 Session Management

  • Idle sessions shall be automatically locked or terminated after 15 minutes of inactivity for standard users and 5 minutes for privileged sessions.
  • Maximum session duration shall not exceed [TO BE COMPLETED BY RAMDOOT SOLUTIONS] hours, after which re-authentication is required.
  • Session tokens shall be unique, unpredictable, and transmitted only over encrypted channels.
  • Session tokens shall be invalidated upon logout and shall not persist across browser or application restarts unless explicitly designed with secure "remember me" functionality approved by the ISO.
  • Concurrent sessions from multiple devices shall be limited to [TO BE COMPLETED BY RAMDOOT SOLUTIONS] per user for sensitive systems.

7.6 Account Lockout

  • User accounts shall be locked after 5 consecutive failed authentication attempts.
  • Locked accounts shall remain locked for a minimum of 30 minutes or until manually unlocked by IT.
  • Administrative accounts shall be locked after 3 consecutive failed attempts and require manual unlock by a separate administrator.
  • Account lockout events shall generate alerts to the IT security team for investigation.

7.7 Password Storage

Passwords shall never be stored in plaintext. All passwords must be hashed using approved algorithms (bcrypt, scrypt, or Argon2id) with appropriate work factors. Password hashes shall be salted with unique, randomly generated salts. Application code or configuration files shall never contain hardcoded passwords.

7.8 Password Transmission

Passwords shall only be transmitted over encrypted channels (TLS 1.2 or higher). Temporary or initial passwords shall be communicated through secure, out-of-band channels and must be changed upon first use.

8. Detailed Requirements

8.1 Password Reset Procedures

Self-service password reset shall be available and must require identity verification through MFA or security questions (minimum 3 questions with answers not easily discoverable). IT help desk password resets shall require caller identity verification through an approved process before resetting credentials.

8.2 API Keys and Tokens

API keys and authentication tokens shall be treated with the same security rigor as passwords. They shall be rotated at least every [TO BE COMPLETED BY RAMDOOT SOLUTIONS] days, stored in a secrets management system, and never committed to source code repositories or shared via email or chat.

8.3 Biometric Authentication

Where biometric authentication is used, biometric data shall be stored locally on the user's device and shall not be transmitted to or stored on Ramdoot Solutions servers. Biometric authentication shall be used as one factor in a multi-factor scheme, not as a sole authentication method for sensitive systems.

8.4 Password Managers

Use of an approved password manager is strongly encouraged for all employees. The approved password manager shall be: [TO BE COMPLETED BY RAMDOOT SOLUTIONS]. Password managers shall be secured with a strong master password and MFA.

8.5 System and Service Account Authentication

Service accounts shall authenticate using certificates, API keys, or managed identities rather than passwords where technically feasible. Where passwords are required for service accounts, they shall meet the same complexity requirements as privileged accounts and be rotated every 60 days.

9. Exceptions

Exceptions to this policy must be formally requested with a written business justification and a risk assessment. Exceptions require approval from the Information Security Officer. All exceptions shall be time-bound (maximum 6 months), documented in the exception register, and reassessed at expiry. Compensating controls must be identified and implemented for any approved exception.

10. Monitoring and Compliance

  • Password compliance shall be monitored through automated tools that report on complexity violations, age, and reuse.
  • MFA enrollment and usage rates shall be tracked and reported monthly.
  • Failed authentication attempts and lockout events shall be monitored in real time.
  • Annual audits shall verify that authentication configurations across all systems meet the requirements of this policy.
  • Penetration testing shall include testing of authentication mechanisms at least annually.

11. Violations and Enforcement

Sharing passwords, writing passwords in plaintext, disabling MFA without authorization, or otherwise circumventing authentication controls constitutes a policy violation. Violations may result in disciplinary action up to and including termination. Suspected credential compromise shall be treated as a security incident and investigated accordingly.

12. Records and Evidence

  • Authentication system configuration documentation.
  • MFA enrollment records.
  • Password compliance scan reports.
  • Account lockout and failed authentication logs.
  • Password reset request logs.
  • Exception request forms and approvals.
  • Penetration testing reports covering authentication.

Records shall be retained in accordance with the Data Retention Policy (RS-POL-007).

15. Review Cycle

This policy shall be reviewed at least annually, or sooner if triggered by:

  • A credential compromise or authentication-related security incident.
  • Changes to authentication technologies or industry best practices.
  • Regulatory or compliance requirement changes.
  • Findings from penetration testing or security audits.
