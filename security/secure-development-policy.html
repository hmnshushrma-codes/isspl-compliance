2. Purpose

This policy establishes the requirements for integrating security into every phase of the Software Development Life Cycle (SDLC) at Ramdoot Solutions. It ensures that applications and systems are designed, developed, tested, and deployed with security as a foundational principle, reducing the risk of security vulnerabilities in production systems and protecting organizational and customer data.

3. Scope

This policy applies to:

  • All software developed internally by Ramdoot Solutions, including web applications, APIs, backend services, and mobile applications.
  • All development, staging, testing, and production environments.
  • Open-source and third-party libraries and frameworks integrated into Ramdoot Solutions products.
  • All developers, QA engineers, DevOps engineers, architects, and development managers.
  • Contractor and outsourced development teams working on Ramdoot Solutions projects.
  • CI/CD pipelines, source code repositories, and associated tooling.

4. Objectives

  1. Embed security into every phase of the SDLC — from requirements through deployment and maintenance.
  2. Prevent common application security vulnerabilities as defined by OWASP Top 10.
  3. Ensure all code is reviewed for security before merging to protected branches.
  4. Automate security testing through static analysis, dynamic analysis, and dependency scanning.
  5. Protect secrets, credentials, and sensitive configuration from exposure.
  6. Maintain clear separation between development, testing, and production environments.

7. Policy Statements

  1. Ramdoot Solutions shall integrate security activities into every phase of the SDLC.
  2. All developers must complete secure coding training within 30 days of joining and annually thereafter.
  3. Threat modeling shall be performed during the design phase of all new applications and significant feature changes.
  4. All code must undergo peer review by at least one other qualified developer before merging to protected branches.
  5. Static Application Security Testing (SAST) shall be integrated into the CI/CD pipeline and executed on every pull request.
  6. Dynamic Application Security Testing (DAST) shall be conducted against staging environments before production deployment.
  7. Software Composition Analysis (SCA) must be performed to identify known vulnerabilities in third-party dependencies.
  8. Secrets, credentials, API keys, and tokens must not be stored in source code, configuration files committed to version control, or client-side code.
  9. Development, testing, staging, and production environments shall be logically separated with distinct access controls and credentials.
  10. Production data must not be used in development or testing environments without sanitization and masking of personally identifiable information.

8. Detailed Requirements

8.1 Secure SDLC Phases

PhaseSecurity Activities
Requirements Identify security requirements; define data classification; establish compliance requirements; document security user stories.
Design Conduct threat modeling (e.g., STRIDE); define security architecture; review authentication and authorization design; identify trust boundaries.
Implementation Follow secure coding standards; use approved libraries and frameworks; implement input validation, output encoding, and parameterized queries; peer code review.
Testing Execute SAST, DAST, and SCA; perform security-focused code review; conduct penetration testing for critical applications; validate OWASP Top 10 coverage.
Deployment Verify security gate passage in CI/CD; confirm environment configuration; validate secrets are properly managed; execute pre-deployment security checklist.
Maintenance Monitor for new vulnerabilities in dependencies; apply security patches; respond to vulnerability reports; conduct periodic security assessments.

8.2 OWASP Top 10 Compliance

All development teams shall implement controls to prevent the following vulnerability categories as defined by the current OWASP Top 10:

  1. A01 — Broken Access Control: Implement role-based access control; enforce server-side authorization checks; deny by default.
  2. A02 — Cryptographic Failures: Encrypt data in transit (TLS 1.2+) and at rest; avoid deprecated algorithms; manage keys securely.
  3. A03 — Injection: Use parameterized queries; validate and sanitize all input; use ORM frameworks where possible.
  4. A04 — Insecure Design: Conduct threat modeling; apply secure design patterns; implement defense-in-depth.
  5. A05 — Security Misconfiguration: Harden default configurations; remove unnecessary features, accounts, and documentation; automate configuration management.
  6. A06 — Vulnerable and Outdated Components: Maintain dependency inventory; scan for known CVEs; update components promptly.
  7. A07 — Identification and Authentication Failures: Implement multi-factor authentication; enforce strong password policies; protect session tokens.
  8. A08 — Software and Data Integrity Failures: Verify software integrity; use signed artifacts; protect CI/CD pipeline integrity.
  9. A09 — Security Logging and Monitoring Failures: Log security-relevant events; integrate with centralized monitoring; establish alerting.
  10. A10 — Server-Side Request Forgery (SSRF): Validate and sanitize URLs; restrict outbound network access; use allow-lists for external resources.

8.3 Code Review Requirements

  • All code changes must be submitted through pull requests (or equivalent merge requests).
  • At least one reviewer shall be assigned who was not the author of the code.
  • Reviewers must evaluate code for:
    • Input validation and output encoding.
    • Proper authentication and authorization checks.
    • Secure handling of sensitive data.
    • Absence of hard-coded secrets or credentials.
    • Error handling that does not leak sensitive information.
    • Adherence to secure coding standards.
  • Code reviews shall be completed within two (2) business days of submission.

8.4 Static and Dynamic Analysis

  • SAST tools shall be integrated into the CI/CD pipeline and configured to block merges when Critical or High severity findings are detected.
  • DAST scans shall be performed against staging environments at least weekly and before any production release.
  • All Critical and High findings from SAST and DAST must be remediated before production deployment.
  • Medium findings shall be tracked and remediated within 30 days.

8.5 Dependency Scanning

  • SCA scans shall be executed as part of the CI/CD pipeline on every build.
  • Dependencies with known Critical or High CVEs must be updated or replaced before production deployment.
  • A Software Bill of Materials (SBOM) shall be generated and maintained for each production application.
  • License compliance checks shall be performed to ensure third-party licenses are compatible with organizational use.

8.6 Secrets Management

  • All secrets (database credentials, API keys, tokens, certificates, encryption keys) must be stored in an approved secrets management system: [TO BE COMPLETED BY RAMDOOT SOLUTIONS].
  • Secrets must not be committed to source code repositories. Pre-commit hooks shall be configured to detect and block secret leakage.
  • If a secret is inadvertently committed, it must be rotated immediately and the repository history cleaned.
  • Secrets shall be rotated at least annually, or immediately upon personnel change or suspected compromise.
  • Access to secrets shall be limited to the systems and personnel that require them, following the principle of least privilege.

8.7 Branch Protection

  • The main/master branch and release branches shall be protected with the following rules:
    • Direct commits are disabled.
    • At least one approving code review is required.
    • All CI/CD checks (including SAST and SCA) must pass before merging.
    • Force push is disabled.
  • Branch protection rules shall be configured at the repository level and auditable.

9. Exceptions

Exceptions to this policy must be documented and approved by the CISO and Development Manager. Exception requests shall include:

  • The specific requirement for which an exception is sought.
  • The justification and risk assessment.
  • Compensating controls.
  • The duration of the exception (maximum 6 months, renewable).

10. Monitoring & Compliance

  • CI/CD pipeline reports shall be reviewed weekly for SAST, DAST, and SCA findings.
  • Code review compliance (all merges require review) shall be monitored continuously through repository analytics.
  • Security training completion rates shall be tracked and reported quarterly.
  • Key metrics:
    • SAST/DAST finding density (findings per 1,000 lines of code).
    • Mean time to remediate security findings.
    • Percentage of merges with required code review.
    • Number of secrets detected in pre-commit scans.
    • Dependency vulnerability count by severity.

11. Violations & Enforcement

  • Code deployed to production without passing mandatory security gates shall be subject to immediate rollback.
  • Developers who commit secrets to repositories shall immediately rotate the affected credentials and report the incident.
  • Repeated violations may result in removal of commit access, additional mandatory training, or disciplinary action.
  • Deliberate circumvention of security controls shall be treated as a security incident.

15. Review Cycle

This policy shall be reviewed at least annually, or sooner if triggered by:

  • Publication of a new OWASP Top 10 edition.
  • Significant changes to the development technology stack or SDLC processes.
  • Security incidents related to application vulnerabilities.
  • Findings from penetration tests or security audits.
